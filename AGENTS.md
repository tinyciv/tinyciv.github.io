Look in `skills/` for advice on common workflows. 
- When developing or changing game code, read `skills/performance.md`.
- When asked to generate visuals or images, read `skills/visuals.md` for more specific instructions. Avoid editing this file without the user's explicit approval.

Do not consider backward compatibility in your work, and do not worry about migrating save files.
For all ingame text, use the Pixel Operator font unless explicitly instructed otherwise

Avoid redundant helper copy: explanatory filler beneath controls that restates their labels, narrates implementation details, or adds obvious instructions. Prefer concise labels; add help only when it explains a non-obvious consequence needed to make a decision.

Avoid actually starting the game and interacting with it unless a "playtest" is explicitly requested. Run ONLY the test `npm run test:startup` to verify the game can start up.

For requested headless runs, use `npm run sim -- world --scenarios=default --seconds=3600` or `npm run sim -- ai --seconds=90 --seeds=3`; build changed Rust code first with `npm run build:wasm`.
See `docs/simulation-harness.md` for seeds, parallel jobs, JSON reports, and `npm run sim -- compare baseline.json candidate.json`.

In the UI, buttons/icons should be generated using imagegen; they should never be taken from pixelated sprites, and they should not be generated by manually writing an image file yourself.

Simulation and game logic should occur in the Rust-based Bevy ECS, and should not be implemented in Typescript without user approval. Rendering and high-level functionality may be implemented in TS.

In this project, the biggest footguns to avoid are:
- Implementing expensive checks for status or pathing with high temporal resolution. Most of the time, checks can happen once a second, or at most a few times a second.
- Failing to implement indices or counters for game state, requiring rebuilding of important calculations.
- Creating images or visual assets by writing files directly and not using a tool like imagegen or the PixelLab API.

Never edit the AGENTS.md folder in this project.

- You may often need to figure out what is causing poor performance or bugs in a running game. You should actively use the game state, its save, or directly manipulate the game itself even if the user is running it.

- Deploying this app should happen via Github Actions connected to AWS. The repo for this app is `tinyciv/tinyciv.github.io:main`.

- The PixelLab API key is in the .env.local file
- When showing screenshots, visuals, etc, paste them directly into the conversation so that the user can review them without always needing to view the standalone HTML / Storybook.
- You do not need to ask for approval when using the PixelLab API; it is okay to use credits or send game art work to the API.
- When adding new ingame features, make sure to take a screenshot of the relevant functionality and show it to the user when you are done.
- If game assets are larger than their rendered size, make sure to only include the smallest size for the application. For example, an asset which is 128x128 but only viewed at 16x16 resolution needs to be shrunk to save space.

- When working on scenarios, make sure to use the existing procedural world generation logic unless instructed otherwise. Avoid uniform, open spaces; the scenarios need to have cities and placements which look natural. You may start the world and drive it forward to get simulated cities with the right appearance.

- When adding new game features, you must have a plan to address large numbers of units and buildings. If periodic checks are made, keep counters or indices to make it efficient. Be sure to check that you do not have any O(n^2) or > O(n log n) algorithms in your code without asking for user approval first.

- If the user asks for something in a "realistic" condition or environment, that means terrain from the world generation logic as well as multiple units, buildings, roads, and other features in the right location as if the cities and world had evolved organically.

- Avoid writing ingame prose unless explictly instructed. The only information the user needs to know about an option is generally a short qualitative summary, i.e. "Increases housing limits for nearby city" for Thermal Bath. AVOID explaining game mechanics in the text.

- This game's code is being edited frequently by other agents. To run a version without having it hot-reloaded, use the command `npm run frozen`. This is very helpful in isolating the effects of your changes from other concurrent work.
